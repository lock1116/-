## 数据库
1、mysql逻辑架构
分为上下两层，server层和存储引擎层
server层：所有存储引擎共用，负责连接管理、语法解析、查询优化、执行调度等。
连接器，管理客户端连接，身份认证，权限管理
分析器，语法和词法分析，生成解析树
优化器，生成执行计划，选择索引，决定表连接顺序
执行器，调用存储引擎接口，逐条/批量执行，返回结果
存储引擎层：负责数据的存储、读取、事务、锁、MVCC等。
采用插件式架构，表级别可独立指定引擎。
常见的存储引擎有innodb和myisam
2、InnoDB和MyISAM存储引擎的区别
InnoDB支持事务，使用的是聚簇索引，可以根据主键查询到数据，支持外键，支持表级锁和行级锁，锁的颗粒度更高；MyISAM不支持事务，使用的非聚簇索引，不支持外键，只支持表级锁。mysql5.7之后默认使用引擎为InnoDB
3、为什么mysql用B+树做索引？
因为随机读写磁盘的速度很慢，B+树是多叉树，一般树高只有2-4次，意味着查询一条记录只有2-4次磁盘i/o，二叉树和红黑树，树高可能会达到十几二十层，就要进行多次磁盘i/o，速度慢。
B+树将所有数据只存储到叶子节点上，且叶子节点中都是用双向链表串联，范围查询时，只要沿着链表遍历。B树的数据是随机存放，范围查询时，必须中序遍历树，导致多次磁盘i/o。
B+非叶子节点只存索引键（Key）和指针，不存具体数据。因此一个16KB的磁盘页能塞进更多索引项，进一步降低树的高度（变得更矮）。B树的每个节点都存数据，导致节点“臃肿”，树变高，I/O次数增加。
不适用哈希表的原因是，哈希表不支持顺序和范围查询。
4、什么是回表，什么是覆盖索引？
回表：查询的数据在辅助索引上找不到，必须拿着主键ID再去主键索引（聚簇索引）查一遍整行数据。
覆盖索引：查询需要的所有字段，都在辅助索引树上直接能拿到，不需要回表。
5、设计数据库表，使用主键
特性维度	自增ID (AUTO_INCREMENT)	UUID	雪花算法 (Snowflake)
核心原理	数据库维护的单调递增数值	基于时间、MAC地址或随机数生成的128位字符串	64位长整型，由时间戳、机器ID和序列号组成
性能表现	极高。写入为顺序追加，索引效率最高，几乎无页分裂	差。写入随机，导致大量页分裂和随机IO，性能可能下降30%-50%	良好。ID趋势递增，接近自增ID的性能，单机每秒可生成数十万ID
存储空间	最小。通常为4或8字节	最大。标准的36字符字符串，占用36字节（二进制存储也需要16字节）	适中。8字节，和BIGINT一样大
全局唯一性	差。局限于单库单表，分库分表时极易冲突	最好。分布式环境下可独立生成，无需中心协调	好。通过工作节点ID和序列号在分布式环境保证唯一
安全性与可读性	差。连续数字易暴露业务规模，易被爬取或枚举	好。无规律，几乎无法猜测，安全性高，但可读性差	中等。趋势递增，安全性优于自增ID，但ID本身也无业务含义
雪花算法的核心问题是依赖系统时间，如果系统时间回拨，会导致Id不再递增甚至重复

自增ID的顺序写入：新数据的主键值总是最大的，InnoDB只需在B+树的最右侧数据页末尾追加记录，空间满了就申请一个新页，几乎不会触发页分裂。这种方式索引友好，写入效率最高。
UUID的随机写入：新生成的UUID是无序的，它可能需要被插入到B+树中任何一个已经排好序的位置。如果目标数据页已满，InnoDB就不得不进行昂贵的页分裂操作，把一半数据移到新页，以腾出空间插入新记录。这个过程会产生大量随机I/O，导致写入性能急剧下降，并造成索引碎片，还浪费存储空间。
选型建议：按场景选择
推荐使用自增ID
典型场景：绝大多数单库单表业务，如后台管理系统、内容管理系统（CMS）。
理由：你的业务不需要跨库唯一ID，且对插入性能有极致要求，那么它依然是最佳选择。
推荐使用雪花算法
典型场景：所有分库分表的业务（如订单、用户表），需要全局唯一ID且追求高性能的分布式系统。
理由：它平衡了高性能与全局唯一性。其趋势递增的特性也解决了UUID导致的索引碎片问题，是分布式架构下的首选方案。
注意事项：需要额外实现或引入组件来生成ID，并要妥善处理时钟回拨问题（例如NTP时间同步导致时钟回拨，可能生成重复ID）。
推荐使用UUID
典型场景：对安全性有极高要求的数据（如用户token、API密钥），或者需要在客户端本地离线生成ID的场景。
注意事项：如果非要用它做主键，建议采用COMB（组合）UUID，将时间戳一部分融入ID，使其具备有序性，缓解索引碎片问题。另外可以用UUID_TO_BIN()函数将其转为16字节的二进制存储，节省空间。
